Receipt OCR harness: architecture and flow

Numbers: 300 SROIE scans, date + total exact match, run of 2026-10-31. Model self-confidence is never used to approve.

1 · Architecture at a glance

  1. 1Receipt image arrivesfile check, resized (1,600 px for cloud, 1,024 px for the local VLM)
  2. 2T1 reads every receipt, locallyRapidOCR text, Tesseract as a second witness, rules pull vendor / date / total
  3. 3T1 sure → auto-accept · 45.0%both OCR readers agree on date and total AND OCR confidence ≥ 0.9
  4. 4Not sure → T3 Gemini Flash-Lite · 55.0%the only step where the image leaves the machine; code checks pass → auto-accept (50.3%)
  5. 5Checks flag T3 → T4 Gemini Flash · 4.7%zero flags → auto-accept (0.3%)
  6. 6Still flagged → human review · 4.3%13 of 300 receipts
  7. BLocal only: step 4 goes to T2 Qwen2.5-VL · 55.0%zero flags → auto-accept (36.7%); flagged → human review (18.3%)
  8. ⚡Gemini 429 / 503 → Claude Haikuone fast-fail attempt, circuit breaker after 3 failures, 60 s cooldown

Code checks 1-4 (no answer key)
  1. sanitizer: NFKC, EN/KO/JA/ZH injection patterns, field whitelist, types
  2. arithmetic: subtotal + tax + tip + discount = total (tolerance 0.05; absent is not zero)
  3. date plausible for the dataset era
  4. two-reader: the model's total and date must appear in the OCR text
What the checks caughtEach reader run alone on all 300: the checks flagged 5 of Flash-Lite's 8 wrong answers, 4 of Flash's 6, and 38 of the local VLM's 51.
The hard part is knowing when to call the cloudAn oracle that knows the answers sends 22.7% to the cloud for 98.7%. The rule signal sends 55.0% for 95.7% (no checks).
